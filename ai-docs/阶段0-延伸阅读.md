# 阶段 0 · 延伸阅读（每个"手法"背后的"机制"）

> 生成：2026-10-09　|　定位：进入阶段1 前的"地图"
> 阶段0 学的是表面招式，这里往下挖一层——每个手法背后都挂着一个阶段1-3 会正式深挖的机制。

## 1. 幻觉：今天学"识别"，治本靠 RAG

- **根因**：LLM 是概率补全，没有"查资料"这个动作，只能从参数记忆里**插值**。所以它顺着 `Execute…Async` 的模式凭空补一个——不是它坏，是它没有"核实"能力。
- **治标（阶段0 学的）**：要出处、拿编译器验证、分步 trace。
- **治本 = RAG（检索增强生成）**：把事实从外部知识库**检索出来塞进 prompt**，让模型"基于给定材料回答"而非"凭记忆回答"。→ 阶段1 W6–W10 要建的核心项目。
- **其他压缩手段**：self-consistency（同问题采样多次投票）、强制每句话标来源、给它工具让它去查。
- **关键认知**：幻觉**不可根除**（概率模型本性），只能压缩。RAG 把"参数记忆"换成"外部检索"，大幅降低但非归零 → 识别能力永远要留着。

## 2. 结构化输出：今天学"单向 JSON"，进阶是 tool calling

- **今天**：你发问 → 模型返回 JSON → 你解析。单向。
- **进阶 = function/tool calling**：你给模型一组**工具定义**（name + description + 参数 schema），模型**自己决定**调哪个、返回结构化调用请求，你执行后**回填**结果，模型再决定下一步 → 这就是 **Agent 的核心循环**（W5 手写、W11–W12 做成带 RAG 工具的 Agent）。
- **演进链**：`json_object`（保证合法 JSON）→ `json_schema`（约束到字段级）→ tool calling（模型主动发起结构化调用）。
- **description 是命门**：模型靠工具的 description 决定"调不调、调哪个"。描述写不好就选错工具或不调 → W11"反复打磨工具描述"的原因。

## 3. token/上下文：今天学"计费"，扩展是"上下文工程"

- **上下文工程（context engineering）**：窗口有限，怎么组织塞进去的内容成了专门学问：
  - **分层**：system（稳定）/ 检索资料 / 对话历史（压缩摘要）/ 当前问题
  - **lost in the middle**：长上下文中部信息易被忽略 → 重要的放**头尾**
  - **摘要压缩**：多轮对话把旧的滚动摘要，别原样堆雪球（W12）
  - **RAG 按需检索 vs 长上下文全塞**：检索更省更准
- **prompt caching（省钱杠杆）**：稳定前缀（system + 固定资料）可被端点缓存，重复调用只算一次 input 费。任务3 那次 `usage.prompt_tokens_details.cached_tokens: 0` 就是这个字段——多轮/批量场景用起来能显著省钱（**该中转是否支持、怎么触发，待实测**）。

## 4. 边界单测：今天学"判用例真伪"，扩展是"验证测试本身的质量"

- **变异测试（mutation testing）**：工具故意往源码注入小 bug（`>=`→`>`、删一行），看你的测试**有没有 FAIL**。没 FAIL = 测试是摆设，只是"跑过"没"测到"。
- **覆盖率陷阱**：100% 行覆盖 ≠ 测得好。覆盖只说"这行执行过"，不说"执行时断言了什么"。**变异测试才检验断言有效性** → 接上任务4 核心洞察："看着在测"和"真能抓 bug"是两回事。
- **.NET 工具**：`Stryker.NET`。

## 5. 读代码库：今天学 grep，扩展是语义检索（embedding）

- **grep 天花板**：字面匹配，找不到"语义相关但字面不同"的东西（搜"登录超时"，代码写 `SessionExpiry` 就抓不到）。
- **embedding + 向量检索**：把代码/文档转成向量，按**语义相似度**召回。
- **这就是 RAG 用在代码上**（W6–W7 embedding + 向量库）。今天读的 `wsaccountmanager` 完全可以做成"**能问答的代码库**"。
