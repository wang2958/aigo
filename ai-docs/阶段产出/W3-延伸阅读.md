# W3 延伸阅读 · 从"手感"到"道理"

> 对应 `学习计划.md` 阶段1·W3（会接·C#/.NET 起步，7/7 收官）。
> W3 学的是**手感**（怎么调通 API）；这篇补的是**手感背后的道理**（为什么这么设计）。
> 因为道理才迁移得动，手感和具体 API 会随版本过期。
> 每节结构：**这样做（recap）→ 为什么这样做（重点）→ 往后连到哪**。

## 扩展 1：为什么包要拆成 Abstractions / AI / OpenAI 三层

**这样做**：装了三个包，业务代码只 `using Microsoft.Extensions.AI`，装配时才碰 `.OpenAI`。

**为什么这样做**：这是**依赖倒置原则（DIP）**的物理落地。核心一句话——*高层业务代码不该依赖具体供应商，两边都该依赖抽象*。

三层的职责边界：
- `Abstractions`：只有 `IChatClient` 这类**接口和数据模型**，零实现、零供应商依赖。最稳的一层，几乎不变。
- `AI`：中间件、DI 集成这些**通用能力**，也不认识任何具体供应商。
- `OpenAI`：**适配器**，把 OpenAI 的 SDK 翻译成 `IChatClient`。唯一"脏"的一层——供应商改协议，只改这里。

如果合成一个包：业务代码 `using` 到的是 OpenAI 的类型，于是"换供应商"从改一行装配，变成改遍全项目。**分层的真正价值不是整洁，是把"变化"关进笼子**——供应商会变（易变），你对 LLM 的调用方式不该跟着变（求稳）。稳定的东西不该依赖易变的东西，这就是 DIP。

**往后连**：W23 把 Agent 接上本地模型（llama.cpp / ONNX）。因为业务代码只认 `IChatClient`，那时只需再装一个本地适配器包、改装配那一行——W3 埋的抽象，三个月后兑现。

## 扩展 2：为什么 key 进 user-secrets，而不是靠 .gitignore

**这样做**：BaseUrl/Model 进 `appsettings.json`（在仓库里），key 进 user-secrets（在仓库外）。

**为什么这样做**：这是**"约定"和"结构"的区别**，也是纵深防御的一课。

- `.gitignore` 是一条**君子协定**：请求 git 别追踪某文件。但只要有人手滑 `git add -f`、文件名写错、或换机器配置没同步，协定就失效。**它依赖"人每次都做对"。**
- user-secrets 是**物理隔离**：文件根本不在项目目录里（在 `%APPDATA%\Microsoft\UserSecrets\<id>\`），git 从设计上就够不着。**它不依赖人做对，而是让"做错"没有入口。**

更深一层，为什么"进过 git 就等于永久泄漏"？因为 git 记住**全部历史**。`git rm` 删掉的文件还躺在上一个 commit 里；`push` 过一次，就永久进了远端和所有 fork。**清理 git 历史里的 secret 极其痛苦且往往清不干净**，唯一正确策略是从一开始就别让它有进去的机会。这跟阶段0 的"不信任"是同一条线——不信任"我每次都会记得"，改用结构让它无法出错。

**往后连**：生产里 user-secrets 只适合本地开发；上线换成 Key Vault / 环境变量 / Secret Manager。原则不变：**secret 的存放要让它"结构上进不了版本库"**。

## 扩展 3：为什么明明有 IChatClient，还要先用 HttpClient 裸调一遍

**这样做**：任务3 手写 POST、拼 Bearer、挖 `choices[0].message.content`；任务5 才换成一行 `response.Text`。

**为什么这样做**：因为**"抽象泄漏定律"（Law of Leaky Abstractions）**——所有非平凡的抽象，迟早会在某处漏出它底下的细节。IChatClient 帮你藏了 HTTP，但藏不住网络超时、429、供应商特有字段（你已经在 `reasoning_content` 上撞到了）。

只学过抽象、没学过裸调，泄漏发生时你会**两眼一抹黑**：`response.Text` 是空的，你不知道底下 HTTP 返回的 JSON 里其实有内容、只是抽象没映射上来。而裸调过的人，第一反应是"把原始 JSON 打出来看"——因为你亲手摸过那层血肉。

所以教学顺序是刻意的：**先见血肉（HTTP + 原始 JSON），再见骨架（IChatClient）**。抽象的价值是省重复劳动，不是替你理解。你可以永远用 IChatClient 写生产代码，但必须**知道它下面在干什么**，才能在它漏的时候补上。

**往后连**：扩展 7 讲泄漏真发生时怎么逃生。W4 的流式输出（SSE）也是同理——先看裸的 `text/event-stream` 长什么样，再理解 `StreamAsync` 在替你做什么。

## 扩展 4：为什么必须检查 finish_reason，不能拿到 content 就用

**这样做**：任务4 把 `finish_reason` 当状态机拆：`stop` / `length` / `tool_calls` / `content_filter`。

**为什么这样做**：`finish_reason` 是你和模型之间**这次调用的"终止条款"**——告诉你答案是"正常说完的"还是"被掐断的"。不看它就等于**调用函数不看返回值**。

- `stop`：模型自然说完。答案可信，可以用。
- `length`：**被 `max_tokens` 截断了**。答案不完整——JSON 可能只输出一半、代码断在中间。直接拿去解析会得到诡异错误，而根因不在数据里，在"你没给足 token 预算"。
- `tool_calls`：模型没想给文本，它想调工具（W5 核心）。此时 `content` 往往是空的，真正内容在 `tool_calls` 字段。
- `content_filter`：被安全审查拦了。

把 `length` 和 `stop` 混为一谈，是新手最常见的隐性 bug：**输出莫名其妙断掉却查不到原因**，因为代码从没看过 finish_reason。这也是 W2 token 计费那课的延续——`max_tokens` 是预算，`length` 就是预算超支的信号灯。

**往后连**：W4 的"上下文截断策略"直接依赖它——主动管理 token 预算，避免频繁撞上 `length`。W5 的函数调用完全建立在"识别 `tool_calls`"上。

## 扩展 5：为什么 IChatClient 的四大价值里，"中间件管道"最重要

**这样做**：任务5 总结抽象四价值——供应商无关、强类型、中间件管道、可 mock。

**为什么这样做（重点讲中间件）**：前三个是"省事"，只有中间件管道是**架构能力的地基**。它用**装饰器模式（Decorator）**：一个 `DelegatingChatClient` 包住真正的 client，在"调用前"和"调用后"插入逻辑，再原样往下传。

想象一个洋葱，请求从外层穿到内层，响应再从内层穿回外层：

```
你的代码
  └─ Logging（记一条日志）      ← 出：记录响应
      └─ Retry（失败就重试）    ← 出：判断要不要重来
          └─ 真正的 OpenAI client → 发 HTTP
```

装配（W4 会真写）：

```csharp
IChatClient client = new OpenAIClient(...).GetChatClient(model).AsIChatClient()
    .AsBuilder()
    .UseLogging()      // 自动记录每次调用
    .UseRetry()        // 自动重试瞬态错误
    .Build();
```

**为什么这个结构厉害**：重试、日志、限流、缓存这些"横切关注点"，本来会散落在每一个调用点、重复写几十遍。中间件把它们**抽成一层层可插拔的壳**，业务代码一行都不用改。这跟 ASP.NET Core 的中间件、C# 的 `DelegatingHandler` 是同一个思想。

**往后连**：W4 的"异常与重试：429、指数退避"不是手写 try-catch 循环，而是用 `.UseRetry()` 配出来。扩展 6 的重试策略，就通过这个管道挂上去。

## 扩展 6：为什么异常要按"能不能重试"分类，而不是一律 try-catch

**这样做**：任务6 分层捕获 `ClientResultException`（HTTP 错）/ `HttpRequestException`（网络）/ 兜底，给不同状态码不同处理。

**为什么这样做**：因为**重试只对"瞬态错误"有意义**，对"永久错误"重试是纯浪费甚至有害。判断标准是**瞬态性**：

| 错误 | 性质 | 该怎么办 | 为什么 |
|---|---|---|---|
| 401 未授权 | 永久（配置错） | 不重试，报配置 | key 错了，重试一万次还是错 |
| 404 模型不存在 | 永久（配置错） | 不重试，报配置 | 名字错了，重试无意义 |
| 429 限流 | 瞬态 | **退避后重试** | 服务器让你慢点，等一下就好 |
| 5xx 服务端错 | 瞬态 | 重试 | 对方抽风，可能下次就成 |
| 网络超时 | 瞬态 | 重试 | 链路抖动 |

把 401 也塞进重试循环，是典型错误——**它不会自愈，你只是在浪费三次调用后报一个更晚、更模糊的错**。正确分类让错误"尽早、尽准"暴露（呼应 W1"兜底越温柔，bug 潜伏越久"）。

再深一层，**为什么退避要"指数 + 抖动（jitter）"**，而不是固定等 1 秒重试三次？
- 固定间隔重试 → 服务器刚缓过来，你和成千上万客户端**同一时刻又一起打过去**，二次压垮。这叫**重试风暴 / thundering herd**。
- 指数退避（1s → 2s → 4s）给对方喘息时间；加随机抖动（±随机毫秒）让所有客户端重试点**错开**，不再同步撞击。

**往后连**：.NET 有现成的 `Microsoft.Extensions.Resilience`（底层 Polly），标准管道 `AddStandardResilienceHandler()` 把"重试+退避+抖动+熔断+超时"打包好。W4 通过扩展 5 的中间件管道挂上去。生产级 LLM 应用这一层几乎必需，因为 429 是常态。

## 扩展 7：抽象漏了你要的字段（reasoning_content），三条逃生路

**这样做**：任务5 发现 `response.Text` 拿不到 `reasoning_content`。

**为什么这样做（扩展 3"抽象泄漏定律"的实战应对）**：当抽象吃掉了你需要的东西，三条路，按代价从低到高：

1. **挖逃生口**：响应里通常带 `RawRepresentation`（原始供应商对象）或 `AdditionalProperties`（未映射的额外字段）。先试这个——**保留抽象的其余好处，只捞回被藏起来的字段**。
2. **局部回退裸调**：这一个特定场景用 HttpClient 手挖 JSON。代价是失去强类型和中间件管道，**只在抽象确实补不上时用**。
3. **给上游提 PR / 换适配层**：如果是抽象的设计缺陷、很多人都需要，最彻底的办法是让抽象本身支持它。慢，但根治。

**为什么优先第 1 条**：好的抽象会**预留逃生口**，正因设计者知道"我不可能映射所有供应商的所有字段"（抽象泄漏定律他们自己也认）。`RawRepresentation` 就是"我知道我会漏，漏了你从这里捞"的官方后门。**遇到抽象不够用，先找它有没有留后门，而不是立刻推翻抽象。**

**往后连**：W5 工具调用、W6 embedding 维度参数，都会遇到"通用抽象 vs 供应商特有能力"的张力。"先挖逃生口、再考虑回退"的决策顺序会反复用到。

## W3 → W4-W12 前向地图

| W3 学的 | 为什么是地基 | 在哪周兑现 |
|---|---|---|
| IChatClient 三层抽象 | 换供应商只改一行装配 | W23 接本地模型 |
| user-secrets / 配置分层 | secret 结构上进不了库 | 全程，尤其 W9-W10 部署 |
| HttpClient 裸调 + 原始 JSON | 抽象泄漏时能 debug | W4 SSE、W7 检索调参 |
| finish_reason 状态机 | 区分"说完"vs"被截断"vs"想调工具" | W4 截断策略、W5 工具调用 |
| 中间件管道（装饰器） | 重试/日志/限流可插拔 | W4 重试、W12 成本防护 |
| 异常按"可否重试"分类 | 只对瞬态错误退避 | W4 429 退避、W12 失败恢复 |
| RawRepresentation 逃生口 | 抽象漏字段时捞回来 | W5 工具、W6 embedding |

## 一句话收束

W3 每个"怎么做"背后都是同一个"为什么"——**在"求稳的抽象"和"易变的现实"之间，既要享受抽象的便利，又要始终清楚它替你屏蔽了什么、并保留随时看穿它的能力。** 这条线从 W3 一直贯穿到 W12 的 Agent。
