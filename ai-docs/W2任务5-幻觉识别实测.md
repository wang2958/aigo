# W2 任务5 · 幻觉识别：问不存在的 API，看它编不编（含实测）

> 日期：2026-10-09
> 端点：`https://maas.qianwenaiapi.com/compatible-mode/v1`，模型 `qwen3.8-max`（推理模型）
> 方法：真调 3 个探针——2 个不存在的 .NET API + 1 个真实 API 作对照

---

## 实测结果

| 探针 | 是否真存在 | 模型行为 | 延迟 | total(含思考) |
|---|---|---|---|---|
| 假A `String.CompareFuzzy` | ❌ 不存在 | ✅ **识破**："这个前提不成立，.NET 8 没有此方法"，并给了反射验证法 | 216s | 9365（思考8057） |
| 假B `SqlCommand.ExecuteJsonAsync` | ❌ 不存在 | ❌ **彻底幻觉**：编出返回类型 `Task<JsonDocument>`、与 ExecuteReaderAsync 的对比表、示例代码 | 205s | 7522（思考6626） |
| 真 对照 `Contains(string, StringComparison)` | ✅ 存在 | ✅ 答对 | 19.4s | 885（思考312） |

地面真相：`String.CompareFuzzy` 与 `SqlCommand.ExecuteJsonAsync` **均不存在**（SqlCommand 只有 ExecuteReaderAsync/ExecuteScalarAsync/ExecuteNonQueryAsync/ExecuteXmlReaderAsync 一族，无 Json 版）。

## 题眼：幻觉为什么"有时不犯、有时犯"

同一模型，两个假 API，一个识破一个编。差别在**"像不像真东西"**：

- `CompareFuzzy` 对 `System.String` **格格不入**（已知方法是 Compare/CompareOrdinal/CompareTo/Equals，"Fuzzy"不在其命名世界）→ 被认出。
- `ExecuteJsonAsync` **完美踩中命名模式**（`SqlCommand` 有一整族 `Execute…Async`，且 `FOR JSON` 真实存在、`JsonDocument` 合情合理）→ 模型顺模式**插值补了一个**，补得以假乱真。

**结论：幻觉最危险的不是"明显离谱"，而是"高度符合真实模式、你差点要信"的。你的 .NET 代码里全是成群命名模式（`Get…Async`/`…Manager`/`…Repository`），AI 在模式里凭空补一个，你看不出破绽。**

## 幻觉识别特征（可操作红旗）

1. **过度具体 + 零对冲**：假B 敢给精确返回类型、对比表，全程无"我不确定/建议核对"。真有把握的回答会带**版本号+出处**；缺对冲 = 红旗。
2. **顺模式补全 ≠ 核实存在**：看它有没有做"这方法到底存在吗"的验证，还是直接开讲用法。
3. **给不出可验证的东西**：假A 模型主动教了 `typeof(string).GetMethod("CompareFuzzy")` 返回 null 的验证法——这正是防幻觉钥匙。

## 怎么防（落地）

- **要求"版本 + 官方文档链接 / 可运行验证"**：编造的 API 给不出真实 URL，也过不了反射/编译。
- **拿编译器当裁判**：最快的 .NET 幻觉验证就是把模型给的代码**真编译一下**——假方法名直接 `CS0117/CS1061`。别信 AI 的"API 存在性"，只信编译器。
- **对模式化 API 名格外警惕**：`Execute…/Get…` 成群出现时，宁可现场验证再采信。
- **成本收获**：模型对"需核实前提"的问题思考爆炸——假A 光思考 8057 token / 216s。让模型"谨慎核实"是有算力代价的。

## 局限

n=1（每探针一次）；假B 恰好踩中强模式、假A 较孤立，属抽样；真实 API 问题分布更广。要更稳可对同批探针跑多次/跨模型比。
