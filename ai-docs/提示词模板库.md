# 提示词模板库

> W1 任务 6 的产出。目标 ≥5 个自己会反复用的模板。**已达成 5/5。**
> 每个模板都是「五手法」的落地：①角色 ②上下文 ③输出格式 ④few-shot ⑤先复述。
> 用法：复制模板 → 把 `{{占位符}}` 换成你的真实内容 → 发给模型。

## 模板 1 · 给真实方法生成边界单测

**适用场景：** 手头一个有分支/边界逻辑的方法（金额计算、状态判断、日期处理、权限校验等），要让 AI 产出能覆盖真实边界的单测，而不是一堆 happy path。

**关键：** `{{已知的真实 bug 或易错点}}` 是整条提示词最值钱的部分——它把你的领域知识注入模型，是它自己永远猜不到的。别省略。

```
【①角色】你是资深 .NET 后端，精通 {{测试框架，如 xUnit}} 和边界值分析。

【②上下文】这是被测方法：
{{贴完整方法源码}}

业务规则：{{用一两句话说清计算/判断顺序、约束条件}}
{{已知的真实 bug 或易错点：我们线上出过 ___，因为 ___}}

【⑤先复述】动手前，先用一句话复述你理解的核心逻辑和关键约束，
确认无误再写。（如果我理解错了顺序/边界，你现在就拦住我）

【④few-shot】照这个风格产出（范本）：
{{贴一个你满意的测试方法，锁定命名风格/框架/断言方式}}

【③输出格式】先用表格列出你打算覆盖的用例：
| 测试方法名 | 输入 | 期望输出 | 覆盖的边界 |
表格确认覆盖全了，再给完整代码，同类用例用 [Theory]+[InlineData] 合并。
重点覆盖：{{列出你最担心的几个边界，如 临界值/空集合/null/负数/溢出}}
```

**验收标准（怎么判断模型输出合格）：**
- 表格里是否出现了你 `{{重点覆盖}}` 里点名的每一个边界？漏了就是没读懂上下文。
- 是否为那个"线上 bug"专门造了回归测试？没有就是把②当耳旁风。
- 期望值自己手算一遍——模型算错边界值很常见（尤其涉及顺序、四舍五入、临界 `>=` vs `>`）。
- 逐条问自己：这个测试**真能抓到 bug**，还是只是"看着在测"？

**首次实战记录：** 2026-10-08 用 `CalcOrderDiscount`（满减+会员折+券叠加）跑通，模型正确产出了 `=1000` 临界、券>总额钳位到 0（回归线上 bug）、Items 为空等边界。

## 模板 2 · 摸清陌生代码库（依赖 / 入口 / 关键路径）

**适用场景：** 接手一个完全陌生的代码库，要在半小时内建起全局认知，而不是逐文件通读。对应 W1 任务3。

**关键：** 两处治幻觉的硬约束——①**先复述探查计划再动手**（跑偏前拦住）；②**每个结论必须附真实文件路径，无法证实的写「未证实」**。读库最大的坑就是 AI 按命名猜逻辑、编造类名方法名。探查步骤要显式写死，别让它自由发挥。

```
【①角色】你是资深 {{技术栈，如 .NET}} 架构师，擅长在不逐行通读的前提下，
靠结构信号（项目文件/入口/依赖声明）快速重建陌生代码库的全局图。

【②上下文】我是有 {{N}} 年经验的 {{技术栈}} 开发，对这个库完全陌生。
我要在 30 分钟内建立整体认知，以便安全定位后续改动点。
不用解释编程基础，直接给架构级结论。
代码库路径：{{路径}}（能访问文件系统就自己探查；不能我再贴关键文件给你）

探查方法（按此顺序，别跳步）：
1. 读解决方案/项目拓扑（{{如 .sln + 各 .csproj}}），画「谁引用谁」的依赖分层
2. 找所有可执行入口（{{如 Program.cs / Controller / *Worker}}），判断每端职责
3. 追一条关键路径：外部输入进来 → 到落库/发消息出去，中间经过哪些层和类
4. 关键路径上每个断言都用 grep/文件内容坐实，不许靠命名猜

【⑤先复述】动手前，用 3-5 行说明你打算怎么探查、准备看哪些文件，等我确认后再执行。

【③输出格式】严格遵守：
## 一、依赖关系   —— 缩进树/箭头图分层，每项目一句话职责，标出空壳/废弃项目
## 二、入口       —— 表格：项目 | 类型 | 作用 | 证据(文件路径:行号)
## 三、关键路径   —— ASCII 流程图画主链路，每一跳标注具体类/方法名和文件路径
## 四、反直觉/踩坑 —— 编码问题、命名误导、历史遗留、疑似废弃代码
## 五、下一步该看哪 3 个文件 —— 给出理由

硬性要求：每个结论附真实文件路径作证据；无法证实的写「未证实」；禁止编造类名/方法名。

【④few-shot】输出片段范本（供你对齐格式）：
## 二、入口
| Api | ASP.NET Web API | 接收设备 HTTP 上报 | Program.cs:23 MapControllers() |
```

**验收标准（怎么判断模型输出合格）：**
- 依赖图里每条边，去对应 `.csproj` 里能不能找到 `ProjectReference`？找不到就是编的。
- 入口表每一行的「证据」列，路径:行号 是真的吗？抽查一两个点开看。
- 关键路径上点名的类/方法，grep 一下是否真实存在——这是幻觉高发区。
- 有没有老实标出空壳/废弃项目？全说成"重要组件"就是没在判断、只在描述。

**首次实战记录：** 2026-10-09 读 `D:\Code_Other3\wsaccountmanager`（WhatsApp 养号系统，6 项目）。走通 `sln→csproj依赖图→Program.cs入口→grep publish/subscribe 坐实 MQ 链路` 四步，产出四层架构 + 两条关键路径（异步养号主链路 / 人工管理链路），并识别出 ConsumerSvc 空壳、GBK 编码乱码、Api 里却调 `AddAccountManagerAdminServices` 命名误导等坑。

## 模板 3 · 排查 bug（分步引导 trace 法）

**适用场景：** 一个"为什么结果不对"的 bug，代码有多分支/状态相关，靠直觉猜容易错方向。对应 W1 任务5、基线"排查 bug"。

**关键：** 核心闸门是**第2步"逐行 trace 具体输入"**——一句话提问让 AI 从"这类代码通常哪儿出错"作答（先验猜测），分步引导逼它从"这一次这个值实际怎么流动"作答（后验追踪）。bug 排查的正确率几乎全押在这一步。每步等确认再进下一步，把它从单向输出变成可纠偏的对话。

```
【①角色】你是资深 {{技术栈}} 工程师，擅长靠"逐行 trace 具体输入"定位 bug，
        而不是凭经验猜原因。

【②上下文】
- 出问题的方法/代码：{{贴源码，或给文件路径:行号}}
- 触发它的具体输入：{{真实的参数值 / 请求体 / 数据}}
- 观察到的错误现象：{{实际返回/报错是什么}}
- 期望的正确结果：{{本该是什么}}
- 我已排除的：{{我已确认不是这些原因：___}}   ← 有就写，能省一半来回

【⑤先复述 + 分步闸门】按顺序走，每步等我确认再进下一步，禁止一上来就给根因：
  第1步：复述这段代码的分支结构和每个 return/throw 的条件，别评价、别猜。
  第2步：拿我给的"具体输入"逐行 trace，说明走到哪一行 return、返回了什么值。
         每个断言标注行号。走到哪条分支不确定时，明说"这里取决于 X 的值"。
  第3步：在出问题的那一行，列出关键变量的实际值（尤其那些"看着该相等其实不等"的）。
  第4步：现在才归纳根因——一句话说清"为什么这个输入会走到错误结果"。
  第5步：给最小修复（只改必要处），并说明怎么验证修好了（补哪条测试/看什么输出）。

【③输出格式】每步单独成段，开头标「第N步」。
【硬性要求】trace 时禁止编造行号或变量值；无法确定的写"未证实，需要我提供 ___"。

【④few-shot】第3步范本：
  第3步：在 :299，countryCode 实际值是 "+1"（原始入参，未归一化），
        比较目标是字符串 "1"。"+1" != "1" 成立 → 进入提前 return 分支。
```

**验收标准（怎么判断模型没在糊弄）：**
- 第2步的 trace 有没有标**真实行号**？点开源码核对一两行，编的行号一眼露馅。
- 第3步有没有把**变量实际值**摆出来？只说"可能不相等"不给值的，等于没排查。
- 它是不是**跳步**了——第1步就抛出根因？那就是又退回"一句话猜答案"，要打断重来。
- 第5步的修复是不是**最小改动**？顺带重构一大片的，多半没锁定真根因。

**首次实战记录：** 2026-10-09 用 `wsaccountmanager` 的 `GetCountryName` 归一化 bug 跑通对比。设定工单"加拿大 416 号被识别成美国"：一句话提问给出 3 个全错/沾边的猜测（CanadaList 缺 416、Substring 截错、lookup 顺序）；分步引导第3步逼出 `:299` 处 `countryCode="+1" != "1"` → 提前 return FirstOrDefault=美国，`CanadaList` 那段根本没执行，一次锁定真根因。最反直觉点：第2步"先 trace 别下结论"几乎决定成败，一句话省下的 token 会以"照错方向改代码"加倍还回去。

## 模板 4 · 代码审查（贴 diff，分三档）

**适用场景：** 审一个 PR / diff / 一段代码，让 AI 挑问题。对应 W2 任务1。

**关键：** 强制 AI 把发现**分「真问题 / 可改进 / 风格偏好」三档 + 每条附行号和依据 + 标确定性**。这是治两种病的药：一是 AI 为显得有用而**制造噪音**（把风格偏好包装成 bug），二是**漏报**真问题。分档 + 确定性逼它诚实分级，你只重点看 🔴 高确定性那几条。

```
【①角色】你是资深 {{技术栈}} reviewer，严格但克制——只报有依据的问题，不堆风格偏好充数。

【②上下文】要审查的 diff/代码：
{{贴 diff 或代码 + 文件路径}}
这个改动的目的：{{想解决什么问题}}
项目约束：{{如 必须兼容X / 不能用Y / 性能敏感点 / 安全要求}}

【⑤先复述】先用 2-3 行说清这个改动在做什么，确认读懂了再审。

【③输出格式】发现分三档，每条附「文件:行号 | 依据 | 建议 | 确定性:高/中/低」：
## 🔴 真问题（会致 bug / 安全 / 数据错误）—— 按严重度排序
## 🟡 可改进（不致错，但更清晰/更稳/更省）
## ⚪ 风格偏好（主观，我多半不采纳）
没把握的降档并说明为什么没把握。

【硬性要求】禁止为凑数编造问题；宁可少报不误报；行号必须真实、可点开核对。

【④few-shot】范本一条：
🔴 确定性高 | PhoneAreaUtil.cs:299 | countryCode 用原始值("+1")比较而非归一化值("1")，
   传"+1"时手机号细分逻辑走不到，一律返回 lookup 首个国家 | 建议：分支判断统一用去'+'后的值
```

**验收标准（怎么判断这次 review 有没有价值）：**
- 三档是否真分开了？全塞进 🔴 = 在制造焦虑，等于没分级。
- 每条有没有**行号 + 依据**？只说"这里可能有问题"不给证据的，当噪音跳过。
- 🔴 里的每一条，你自己能不能确认/复现？确认不了的就不是"真问题"，是待查项。
- 有没有把纯风格（命名、括号位置）混进 🔴？混了说明它没理解"确定性分级"。
- 反向检查：有没有**漏掉你已知的问题**？拿一个你心里有数的 bug 当"探针"，看它抓没抓到。

**首次实战记录：** 待 W2 任务1（审一个自己写过的真实 PR）时回填。

## 模板 5 · 结构化输出（强制 JSON schema，供程序解析）

**适用场景：** 要模型返回程序能**直接反序列化**的 JSON，而不是自然语言。对应 W2 任务2、阶段1 W5（函数调用的前置）。

**关键：** 给**精确 schema** + **边界规则**（缺字段/未知值/非法输入怎么办）+ **一个完整合法样例**。核心是堵住两个漏洞：模型偷偷加解释性文字或 markdown 围栏（导致解析失败），以及缺信息时**编造**而非按约定填空值。

```
【①角色】你是一个只输出 JSON 的数据抽取器。不输出任何解释文字，不加 ```json 代码围栏。

【②上下文】任务：{{从什么输入，抽取什么}}
输入数据：{{贴输入}}

【③输出格式】严格符合此 schema（字段名/类型/必填，一字不差，不多不少）：
{{如：
{
  "countryCode": string,        // 归一化为不带 '+'
  "country": string,            // 无匹配填 ""
  "matched": boolean,
  "confidence": number          // 0~1，无法确定填 0
}}}
边界规则：
- 缺信息时字段填 {{约定：null / "" / 0}}，禁止省略字段、禁止新增字段
- 无法确定时按约定降级（如 confidence=0, matched=false），禁止编造
- 非法/空输入也要返回符合 schema 的结构，不要用自然语言报错
- 只输出 JSON 本体，前后不加任何文字

【④few-shot】
输入：{{样例输入}}
输出：{"countryCode":"86","country":"大陆","matched":true,"confidence":1.0}

【⑤先复述】（批量场景：先只跑 1 条给我确认格式，确认无误再批量）
```

**验收标准：**
- 输出能不能被 `JsonSerializer.Deserialize<T>()` **一次吃下**？有围栏/多余文字/缺字段就是不合格。
- 拿**边界输入**试（空、乱码、超长、字段缺失）——是否仍返回合法 schema，而不是崩成自然语言。
- 有没有**偷偷加字段**或把 `confidence` 越界（>1）？
- 缺信息时是**按约定填空**还是**编了一个值**？后者最危险。

**落地提醒（别只靠 prompt）：** prompt 约束是第一道防线，不保证 100%。生产环境要配合——① API 若支持 `response_format` / `json_schema`（结构化输出模式）就开；② 反序列化失败要**捕获并重试**（把报错回喂给模型让它修正）；③ 用 `record` + 严格反序列化，别用宽松的动态对象。这道"prompt 约束 + 代码兜底"的双保险，正是阶段1 W5 要练的。

**首次实战记录：** 待 W2 任务2（跑通固定 JSON schema 返回）时回填。
